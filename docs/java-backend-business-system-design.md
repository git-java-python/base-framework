# 大厂中常见的业务系统设计及其解决方案（Java 后端 · 可落地实现版）

> 目标：不仅讲“是什么”，还讲“怎么做、为什么这么做、会踩什么坑、有什么替代方案”。

---

## 0. 先给一个统一方法论（做任何业务系统都适用）

在大厂做后端系统，建议统一用下面 5 个视角评审方案：

1. **领域视角**：核心对象是什么？边界在哪？（防止模型混乱）
2. **一致性视角**：强一致还是最终一致？（防止事务失控）
3. **性能视角**：峰值 QPS、RT、容量如何保证？（防止高峰崩溃）
4. **稳定性视角**：故障如何降级、隔离、恢复？（防止雪崩）
5. **演进视角**：未来需求变化时，是否可扩展？（防止重构代价过高）

这 5 个视角，会在每个系统中展开。

## 1. 用户中心与认证鉴权系统

## 1.1 怎么设计（具体实现）

### 模块拆分
- `identity-service`：账号、密码、手机号、三方绑定。
- `auth-service`：登录、签发 token、刷新 token、登出。
- `permission-service`：角色、权限点、数据权限策略。
- `audit-service`：登录日志、敏感操作日志、风控事件。

### 关键表（示意）
- `user`：`id, tenant_id, status, password_hash, created_at`
- `role`：`id, tenant_id, role_code`
- `permission`：`id, perm_code, resource_type`
- `user_role`、`role_permission`
- `data_scope_policy`：数据权限表达式（部门、地域、层级）
- `login_event`：登录 IP、设备、结果、失败原因

### 认证流程
1. 用户输入凭证（密码/验证码/三方 OAuth）。
2. 风控校验（设备指纹/IP 异常/黑名单）。
3. 签发 Access Token（短时）+ Refresh Token（长时）。
4. 网关校验 token，解析用户上下文透传下游服务。
5. 下游服务对高敏操作再次鉴权（双保险）。

### Java 技术栈
- Spring Security + OAuth2 Resource Server（或 Sa-Token）。
- Redis 存 refresh token 黑名单/会话版本。
- Caffeine + Redis 做权限缓存两级加速。

## 1.2 为什么这么设计
- 网关统一认证能减少重复逻辑，服务内兜底能防止绕过网关。
- Access/Refresh 双 token 平衡安全与体验。
- RBAC 先解决 80% 需求，再用 ABAC/数据权限补齐复杂场景。

## 1.3 常见问题
- 权限变更后缓存不一致导致越权或误拒绝。
- JWT 过长导致网关与链路传输开销增加。
- 多端登录策略不清晰（互踢/并存）导致投诉。

## 1.4 更好的替代方案
- **替代 1：集中式会话（不发 JWT）**  
  优点：可即时失效；缺点：每次请求查会话存储，吞吐压力大。
- **替代 2：外部 IAM（Keycloak/Auth0）**  
  优点：标准化能力强；缺点：定制成本与组织依赖高。
- **替代 3：OPA + Rego 策略鉴权**  
  优点：策略可编排、审计友好；缺点：团队学习成本高。

## 2. 订单/交易核心系统

## 2.1 怎么设计（具体实现）

### 领域拆分
- `order-service`：订单创建、状态流转。
- `inventory-service`：库存预占、扣减、回补。
- `payment-service`：支付下单、回调处理。
- `fulfillment-service`：履约发货。

### 订单状态机
- `INIT` → `PENDING_PAY` → `PAID` → `FULFILLING` → `DONE`
- 关闭分支：`PENDING_PAY` → `CANCELLED`（超时未支付）
- 退款分支：`PAID/FULFILLING` → `REFUNDING` → `REFUNDED`

> 状态流转必须单向且可审计，禁止“随意 update 状态”。

### 幂等与一致性
- 下单接口：`Idempotency-Key` + `order_request_log` 唯一索引。
- 支付回调：`channel_txn_id` 唯一索引 + 幂等处理器。
- 一致性：本地消息表（outbox）+ MQ 投递 + 补偿任务。

### 库存扣减策略
- 普通商品：DB 乐观锁 `version` 扣减。
- 热门商品：Redis 预扣 + MQ 异步落库 + 对账修正。

### Java 技术栈
- Spring Boot + MyBatis/JPA + Kafka/RocketMQ。
- Redisson 分布式锁仅用于“极短临界区”，避免大锁。

## 2.2 为什么这么设计
- 状态机显式化可以避免“魔法状态”导致的业务错乱。
- Outbox 模式让“写库 + 发消息”接近原子语义，工程上最稳。
- 库存分层策略兼顾一致性与吞吐。

## 2.3 常见问题
- 锁粒度过粗造成吞吐下降。
- 回调重试导致重复推进状态。
- 补偿任务没有幂等，二次污染数据。

## 2.4 更好的替代方案
- **替代 1：SAGA 编排（Seata Saga/自研）**  
  适合长事务；但运维与排障复杂。
- **替代 2：TCC**  
  一致性强，但业务侵入高，开发成本大。
- **替代 3：事件溯源（Event Sourcing）**  
  审计能力强，但查询侧复杂，需要 CQRS 配合。

## 3. 营销与优惠系统

## 3.1 怎么设计（具体实现）

### 核心子域
- 活动中心：活动配置、生命周期管理。
- 优惠券中心：发券、领券、核销、回滚。
- 结算引擎：多种优惠叠加计算。

### 规则建模
- 规则 = 条件（人群/商品/时间）+ 动作（减/折/赠）+ 约束（互斥/上限）。
- 采用 JSON DSL 或 Drools DRL。
- 规则版本化：`rule_id + version`，灰度发布。

### 结算链路
1. 拉取用户可用券、活动候选集。
2. 进行规则裁剪（按场景/品类/优先级）。
3. 执行最优解计算（贪心/动态规划）。
4. 输出明细（每一笔优惠来源可解释）。

### Java 技术栈
- Drools（复杂规则）或 Aviator（轻表达式）。
- Redis 缓存规则快照，失效通知走 MQ。

## 3.2 为什么这么设计
- 规则外置，避免每次活动都改代码上线。
- “可解释明细”是客服与风控的关键能力。

## 3.3 常见问题
- 规则冲突与优先级失控。
- 计算复杂度高，导致结算页 RT 波动大。
- 防刷策略只做限流，漏掉设备画像与行为模型。

## 3.4 更好的替代方案
- **替代 1：预计算优惠包**  
  降低实时压力，但实时灵活性下降。
- **替代 2：在线 ILP 求解器**  
  最优性更高，但工程复杂度和算力成本更高。
- **替代 3：规则+模型融合**  
  用模型做“优惠推荐”，规则做“边界约束”。

## 4. 搜索与推荐系统（业务侧）

## 4.1 怎么设计（具体实现）

### 搜索链路
- 数据入湖/入仓 → 索引构建（全量+增量）→ 在线检索（召回+排序）→ 策略重排。
- 索引字段：标题、类目、品牌、价格区间、库存状态、热度分。

### 推荐链路
- 召回层：热门召回、协同过滤、向量召回（ANN）。
- 粗排层：轻量模型（LR/GBDT）。
- 精排层：深度模型（DNN）。
- 重排层：业务规则（多样性、新品保护、去重）。

### Java 落地
- 检索：Elasticsearch/OpenSearch + BulkProcessor。
- 推荐服务：Spring Boot + gRPC 调用模型服务。
- 超时策略：例如 80ms 未返回就降级到热榜。

## 4.2 为什么这么设计
- 分层召回/排序可在“效果与时延”间做精细权衡。
- 重排层确保业务目标（GMV、新品曝光、公平性）。

## 4.3 常见问题
- 特征延迟导致“推荐不实时”。
- 只追求点击率，造成长期价值下降。
- 索引刷新策略不当，写扩散严重。

## 4.4 更好的替代方案
- **替代 1：向量数据库一体检索（Milvus/pgvector）**  
  语义能力强，但运维与成本需评估。
- **替代 2：Learning to Rank 全链路**  
  效果好，但特征与标注体系建设成本高。
- **替代 3：检索增强规则引擎**  
  适合冷启动阶段，快速可控。

## 5. 结算/账务系统

## 5.1 怎么设计（具体实现）

### 账务核心模型
- 账户（Account）
- 分录（Entry）
- 凭证（Voucher）

每笔业务交易生成一组平衡分录（借贷恒等）。

### 关键约束
- 账务流水只增不改。
- 任何冲正必须反向分录，禁止直接改余额。
- 每日余额 = 昨日余额 + 当日分录汇总。

### 对账链路
- 上游订单对账、支付渠道对账、总账对账。
- 差异分类：漏单、重复、金额不一致、状态不一致。
- 自动修复 + 人工工单闭环。

### Java 落地
- Spring Batch 跑日终任务。
- 分片执行（按租户/账户范围）+ 幂等检查点。

## 5.2 为什么这么设计
- 借贷分录天然可追溯，满足审计与合规。
- “只增不改”可降低数据腐化风险。

## 5.3 常见问题
- 账户模型设计过早绑定业务，后续难扩展。
- 对账只做 T+1，无法及时发现线上问题。

## 5.4 更好的替代方案
- **替代 1：实时流式对账（Flink）**  
  发现更快，但建设成本更高。
- **替代 2：专业账务中台产品化**  
  复用能力强，但定制和迁移复杂。

## 6. 通知与消息中心

## 6.1 怎么设计（具体实现）

### 统一消息模型
- `message_task`：消息主任务（业务类型、优先级、模板）
- `message_target`：接收人列表
- `message_delivery`：通道投递记录（状态、重试次数、供应商回执）

### 投递流程
1. 业务系统提交发送请求。
2. 模板渲染（变量替换、多语言）。
3. 路由策略选择通道/供应商。
4. 异步投递 + 回执更新。
5. 失败进入重试队列，超限进死信。

### Java 落地
- 渠道 SPI：SMS/Email/Push/站内信统一接口。
- Resilience4j 做超时、重试、熔断。

## 6.2 为什么这么设计
- 统一模型便于横向扩展新通道。
- 投递与业务解耦，保护核心链路时延。

## 6.3 常见问题
- 重试策略粗暴导致用户重复收到。
- 供应商切换缺少灰度能力。

## 6.4 更好的替代方案
- **替代 1：多供应商实时比价路由**  
  成本更优，但策略更复杂。
- **替代 2：托管通知平台**  
  上线快，但可控性与数据沉淀受限。

## 7. 数据中台 / 报表系统

## 7.1 怎么设计（具体实现）

### 链路分层
- ODS：原始层（保真）。
- DWD：明细标准化。
- DWS：主题汇总。
- ADS：应用指标层（报表/API 服务）。

### 指标治理
- 指标字典（定义、口径、负责人、生效版本）。
- 指标血缘（来源表、加工任务、下游消费）。
- 指标变更评审机制。

### Java 落地
- 查询网关（限流、鉴权、SQL 审计）接入 ClickHouse/Doris。
- 常用报表走缓存与物化视图。

## 7.2 为什么这么设计
- OLTP/OLAP 分离，避免分析查询拖垮交易库。
- 指标治理能解决“同数不同表”的组织协同问题。

## 7.3 常见问题
- 指标口径无 owner，长期漂移。
- ad-hoc 查询无限制，挤占线上资源。

## 7.4 更好的替代方案
- **替代 1：Lakehouse（Iceberg/Hudi + Trino）**  
  灵活统一，但运维门槛较高。
- **替代 2：语义层 BI 平台**  
  口径统一更强，但初期建设周期较长。

## 8. 横向通用能力：怎么落地才有效

## 8.1 高可用
- 限流（网关/服务双层）
- 熔断隔离（线程池/舱壁）
- 降级（返回兜底数据、关闭非核心功能）
- 多机房容灾（同城双活/异地灾备）

## 8.2 可观测性
- 日志：统一 traceId。
- 指标：RED + USE（请求率/错误率/时延 + 资源利用）。
- 链路：OpenTelemetry + SkyWalking/Jaeger。

## 8.3 稳定性工程
- 压测分层：接口压测、链路压测、全链路压测。
- 混沌演练：下游超时、DB 故障、MQ 堵塞演练。
- 预案闭环：发现→止血→复盘→治理项追踪。

## 9. 典型“设计选型对照表”

| 设计问题 | 推荐默认方案 | 适用场景 | 主要代价 | 可选替代 |
|---|---|---|---|---|
| 分布式一致性 | Outbox + MQ + 补偿 | 大部分交易链路 | 最终一致延迟 | TCC / Saga |
| 幂等 | 幂等键 + 唯一索引 | 回调/重试场景 | 表设计复杂 | 状态机幂等 |
| 热点库存 | Redis 预扣 + 异步落库 | 秒杀/大促 | 对账复杂 | 全 DB 串行扣减 |
| 权限控制 | RBAC + 数据权限扩展 | 中后台系统 | 模型演进成本 | ABAC / OPA |
| 报表查询 | OLAP 引擎 + 查询网关 | 多维聚合查询 | 数据链路建设 | 直查业务库（不推荐） |

## 10. 一个务实的 Java 后端实施路线（90 天）

### Day 1~30：正确性优先
- 建状态机、幂等、异常码规范。
- 核心接口补齐单测/集成测试。
- 建立最小可用监控面板（错误率、RT、QPS）。

### Day 31~60：扩展性优先
- 引入 MQ 解耦非核心链路。
- 规则配置化（营销/权限/风控）。
- 核心缓存策略落地（热点隔离、穿透保护）。

### Day 61~90：稳定性与治理
- 完成一次全链路压测 + 容量评估。
- 建立故障演练与 SLO 管理。
- 完成对账、补偿、审计闭环。

## 11. 最后总结

大厂业务系统设计不是“堆技术名词”，而是：
- 在正确的地方用正确的一致性模型；
- 用状态机、幂等、审计把复杂度关进笼子；
- 用缓存、异步、降级把高并发和故障影响控制在边界内；
- 用指标与治理机制让系统可持续演进。

- 营销最优优惠计算：`PromotionEngine`

- 场景化方案库（设计/原因/隐患/优化）：`ScenarioSolutionService`

### 12.1 关键 API

1. `GET /playbook/scenarios`  
   返回不同业务场景的处理方式、原因、隐患和优化建议。
2. `POST /playbook/orders`  
   创建订单（带 `requestId` 幂等键），自动库存预占并写入 outbox 事件。
3. `POST /playbook/orders/{orderId}/pay?channelTxnId=xxx`  
   处理支付回调（`channelTxnId` 幂等）。
4. `POST /playbook/orders/{orderId}/cancel`  
   取消订单并回补库存。
5. `GET /playbook/promotions/best-offer?amount=188`  
   获取当前可用规则下的最优优惠结果。
6. `POST /playbook/notifications/send?bizId=...&receiver=...&content=...`  
   执行消息去重+频控后的发送。
7. `GET /playbook/outbox`  
   查看 outbox 事件列表。

### 12.2 说明

该实现偏“架构演示”而非生产版本，重点展示：
- 不同业务场景应采用的治理策略；
- 为什么这样设计；
- 有哪些隐患与如何演进优化。

在生产环境中，建议把内存实现升级为 Redis/数据库/MQ，并补齐审计、告警、重试、对账等治理链路。

## 13. 扩展实现：微服务 / 高并发 / 多线程 / 设计模式 / 分布式事务 / 中间件

本仓库新增了覆盖上述场景的代码实现，统一通过 `/playbook/**` 调用。

### 13.1 微服务治理（聚合 + 熔断 + 降级）
- 实现：`MicroserviceOrderFacade` + `CircuitBreaker`。
- 怎么处理：订单主数据可用时，用户服务失败走降级数据。
- 为什么：避免下游故障拖垮核心链路。
- 隐患：降级数据可能造成业务偏差。
- 优化：接入服务网格、重试预算、舱壁隔离、降级标识透传。

### 13.2 高并发与多线程
- 实现：`HighConcurrencyService`。
- 怎么处理：
  1) 秒杀链路使用 `Semaphore` 限流 + 原子库存扣减；
  2) 批处理使用 `CompletableFuture` + 有界线程池并行计算。
- 为什么：削峰、防止线程与队列失控。
- 隐患：单机内存库存不适合多实例；线程池参数不当导致延迟飙升。
- 优化：Redis/Lua 扣减、线程池隔离、拒绝策略监控。

### 13.3 设计模式落地业务
- 实现：`DesignPatternPlaygroundService`。
- 怎么处理：策略模式封装支付算法，工厂模式统一创建，责任链做校验扩展。
- 为什么：减少 if-else 分支爆炸，增强可扩展性。
- 隐患：过度抽象会让排障复杂。
- 优化：SPI 自动装配 + 配置化开关。

### 13.4 分布式事务（Saga / TCC）
- 实现：`DistributedTransactionService`。
- 怎么处理：
  - 默认 Saga（本地事务 + 补偿）；
  - 资金强一致链路可选 TCC。
- 为什么：按业务重要性分层一致性策略，避免全链路强一致带来的高成本。
- 隐患：补偿失败与中间态。
- 优化：补偿幂等、重试队列、死信与人工对账。

### 13.5 中间件结合业务
- 实现：`MiddlewareIntegrationService`。
- 覆盖：缓存（读多写少）、MQ（事件解耦）、分布式锁（临界区保护）。
- 为什么：性能与解耦并重。
- 隐患：缓存击穿、消息重复、锁误释放。
- 优化：布隆过滤器+热点永不过期、幂等消费、看门狗续期。
